## P1 — data-loss or wrong-answer risk

### 1. Garmin prunes on a listing that may not have been an enumeration

`garmin/src/ingest/mod.rs` `items()` re-reads five whole-account
listings (personal records, gear, badges, workouts, goals) and then
`prune_items(kind, keep)` deletes every stored row of that kind the
listing did not name. Three ways `keep` is empty without the account
being empty:

- A wrapped response with no array inside falls to
  `.unwrap_or_default()` (`mod.rs:693`) — the exact pattern the
  ingestion doc names as "now a correctness bug rather than a
  convenience" (§"What limits it").
- `Fetched::Nothing` — a 204, a 404, or a 200 with an empty body
  (`api.rs:110,119`) — becomes `Vec::new()` (`mod.rs:697`), so a
  renamed endpoint or a changed `display_name` in the
  `personalrecord` path prunes every personal record.
- `workouts` and `goals` are fetched once with `limit=1000` and no
  paging (`mod.rs:676,680`); activities page, these do not. The
  1001st workout is pruned every run.

The rows survive in history, so nothing is destroyed, but every run
after the failure records a spurious `removed` diff and the store
reads as if the account lost the data. The doc's own sentence: "the
hard part is not the deletion, it is establishing the enumeration was
complete." A listing that did not come back as an array is not an
enumeration and must not prune; `workouts` and `goals` need the paging
`activities()` already has.

### 2. Garmin's failure paths bypass the sink #570 built

The `phase!` macro (`mod.rs:175`) turns a whole failed phase —
`devices`, `daily`, `weight`, `activities`, `wellness`, `items` — into
one `warn!` and `s.errors += 1`; the run then exits 0 with a summary
nobody reads back. `garmin_items_failed` (`mod.rs:699`) does the same
for a listing and records nothing at all. Meanwhile the same crate
already calls `record_object_error` for a failed day (`mod.rs:401`),
so the pattern is half-adopted.

The provider tail in [`plans/problem_visibility.md`](plans/problem_visibility.md)
§3 lists Garmin among the four that adopted `record_object_error`,
which is true of the per-day path and not of the phase or listing
paths. A phase that fails is closer to what `download_problems::report`
records (a configured thing upstream will not serve) than to a
per-item blip; and a listing that fails should also be what stops
finding 1's prune. This is the "better error propagation" now in the
tree, and Garmin should be moved onto it rather than kept on the
counter.

### 3. `datalib_history` reads the working set from `datalib-http`

`history/src/lib.rs::table_sizes` runs `SELECT COUNT(*) FROM "t"` on a
read-only handle. Its doc comment says "Row count of every user table
at HEAD"; a plain `SELECT` reads doltlite's working set, which lives in
the file and is shared across processes — exactly the sentence
`pin/src/lib.rs` opens with. While a sync is writing, the Manage
screen's commit-history panel shows HEAD counts that include
uncommitted rows, and every older commit's count (walked back through
the diffs) is off by the same amount.

AGENTS.md's reader rule is "opens read-only **and pins a commit**".
`datalib_pin` landed the same week with the same third-party-only
dependency profile, so `history` can link it, resolve HEAD once, and
count through `dolt_at_<t>(hash)`. It also re-implements `open_reader`
that `pin` already exports. (Its other statements — `dolt_log`,
`dolt_commit_ancestors`, `dolt_diff_summary`, `dolt_diff_stat` — are
covered by `doltlite_two_process_test`, which is the vetting the rule
asks for.)

### 8. `claude_code` promotes payload-derivable fields to stored columns

`RecordRow` (`claude_code/src/ingest/schema_raw.rs:43`) stores
`session_id`, `record_type`, `timestamp`, `parent_uuid` and
`is_sidechain` beside a `payload` that is "the line as written" — so
all five are `payload->>'$.…'`. The ingestion doc: "Fields derivable
from the payload … should **not** be duplicated as stored columns";
index over the payload or add a VIRTUAL column. `TranscriptRow`'s
columns are writer-synthesized from many records and are fine.

### 9. Facebook diverges from the download rules in three places

Each is stated in `facebook/INGEST.md`, which is the right first
step; the ingestion doc asks that divergences be "either justified or
fixed", and these are stated rather than argued:

- No `<t>_bookkeeping` sidecar, and a hand-rolled chunked
  `INSERT OR REPLACE` (`ingest/mod.rs:250`) instead of
  `bulk_upsert_in_tx` / `ON CONFLICT(id) DO UPDATE` — the doc's "one
  shape, everywhere". `claude_code` and `airvisual` also skip the
  sidecar and say why (a re-read-whole file would churn it), which is
  a justification the doc should carry once rather than three
  INGEST.md files separately.
- Records with no `fbid` get `uuidv5(table, canonical JSON)` — an
  identity that changes on every edit. The doc rules content hashes
  out as identity by name. For an export where nothing more stable
  exists it may be the only option; the doc should say when that is
  allowed.
- Tables are created dynamically from export paths
  (`canonical_table`), so `schema_raw.rs` declares one table. The
  identifier is sanitized and the `AssertSqlSafe` block says so; but
  "the schema is the design" has no home for a source whose tables
  are discovered.

The column is still in `GridRow`, in `api.ts:63`, and

update the `grid_rows.md` example that uses it as the sample column.

### 12. Comments the rule says to delete on sight

Changelog-style, outside tests:

- `scripts/lint_repo.py:330-337` — a dated narrative ("Slack was the
  first (#103) … Gmail … (2026-09-15)"). The rule is stated in the
  ingestion doc; the comment should point there.
- `http/src/lib.rs:1413` `SyncJobView` — "the two answers every reader
  used to derive from `state` for itself".
- `ui/src/cards/SourcesCard.ce.vue:121` — a `///` block (not a
  TypeScript syntax) saying "it used to clear only on the next action".

The `/// It used to …` lines on tests (`subprocess.rs:709`,
`grid_index.rs:2421`, `blob_cas.rs:906`, `doltlite_raw.rs:1858`,
`status.rs:603,663`) are the kind the rule allows: a sentence naming
the regression.

Scale, not a specific defect: 457 non-test functions added this week
carry a `///` block. Most are contract statements ("`None` on the
writer's handle"); a minority restate the name (`snapshot` → "The
newest run.", `now_split` → "Now, as the store keeps it.",
`prune_devices` → "Delete the devices the registration listing no
longer names."). The rule says delete function-level doc blocks on
sight; the tree's practice is to write them everywhere. One of the two
should change.
