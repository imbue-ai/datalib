# Audit: every doltlite claim in the tree, against doltlite 0.50.13

A record, not reference. The pin moved from 0.50.3 to 0.50.12 (#823)
and then to 0.50.13 (#892) in one week, and the docs and comments still
described 0.50.3 — and in places 0.11.x. Every behavioural claim about
doltlite in the tree's 84 docs and its code comments was re-checked on
0.50.13, against fresh stores, by probe or by the two-process harness.
The facts that survived now live in one place,
[`docs/dev/doltlite.md`](../doltlite.md) § "How doltlite behaves", and
[`//datalib/backend/doltlite_facts:doltlite_facts_test`](/datalib/backend/doltlite_facts/doltlite_facts.rs)
checks each single-process one; run against 0.50.12 it fails exactly the
seven facts 0.50.13 changed. Everything else now links there.

**What was done about it, same change.** Every finding below was fixed
in the doc or comment that made it, and engine explanations outside
`doltlite.md` were cut to our rule plus a link. `plans/writer_branches.md`,
`hack/doltlite_fork_bug/` and `hack/sqlx_doltlite_loadtest/` were deleted:
the first had landed and its facts moved, the other two reproduced bugs
0.50.13 no longer has.

## What was wrong, most misleading first

1. **"A process that moves a ref refuses the writer's seals"** (AGENTS.md,
   `etl/README.md`, `plans/paged_grids.md`). True of 0.50.3 (1–2 of 300
   seals refused, one hang). On 0.50.12 and 0.50.13 the same harness
   refused 0 of 1,500; 0.50.3 refused 3–100 of 500 in the same runs.
   A refresh with no pause at all still starves the writer.
2. **"`dolt_at_` is the only snapshot primitive a read-only connection
   has"** (`plans/writer_branches.md`, and assumed by AGENTS.md,
   `etl/README.md`, `pin.rs`). A read-only open of `<store>@<commit>` is
   detached, pinned and indexed; on our file names from 0.50.13
   (dolthub/doltlite#3231). Three such readers beside 500 seals wrote
   0 bytes and saw 0 errors.
3. **"`dolt_at_` and `dolt_history_` push no predicate; `uuid = ?`
   scans"** (`paged_grids.md`, `docs/dev/doltlite.md`, fsindex and
   lightroom INGEST, `dirtree_diff/README.md`). Both seek a primary-key
   equality on a text key from 0.50.12: history on one key went from a
   20 s scan to under 10 ms.
4. **"Filter `dolt_diff_<t>` with `from_ref`/`to_ref`, not
   `from_commit`/`to_commit`"**, and "bound the walk with
   `from_ref = '<old>..HEAD'`" (`doltlite.md`, fsindex INGEST,
   `hack/doltlite_concurrent_reader`). All three spellings agree now; a
   range is one comparison, so that "bound" silently changed the answer.
5. **"A keyless table is diffed by row multiset"** (`sqlite_mirror`
   comments, lightroom INGEST). It is keyed by a hidden rowid and paired
   by position: drop and refill with one row gone reads as a run of
   `modified`.
6. **The lock model** (`etl/README.md`, `doltlite_raw.rs`): doltlite
   `flock`s the store, and `dolt_commit` takes its lock without waiting.
   Its lock is a `.<name>-lock` sidecar held per write transaction, and
   every writer waits in the busy handler. The 0.11.x fork-inherited
   lock is gone.
7. **Three reasons in `doltlite_raw.rs` that were false while the code
   they guard is still right**: `dolt_diff` "only for tables at HEAD";
   `dolt_reset --hard` "refuses" the initialization commit (it succeeds
   and breaks the `dolt_clean` after it); `journal_mode` "rejected" (it
   is inert).
8. **"About 50 ms per auto-committed statement"** (`grid_index.rs`,
   `indexed_markdown.rs`, `plans/one_mode.md`). Well under 1 ms on
   0.50.13; `dolt_commit` about 0.2 ms, not ~20 ms.
9. **"A stray CLI writer gets `commit conflict`"** (`doltlite.md`,
   `agent_user.md`). Its commits vanish when the next seal moves `main`
   over them; the visible symptom is `database is locked`.
10. **Smaller, each in one or two places**: `dolt_schemas` is views and
    triggers, not a schema diff; `dolt_gc` may run before `dolt_commit`
    (the "failed to flush" ordering is gone); FTS5 is compiled in;
    `rowid` on a text key is a hash, not hidden; reaping keeps history;
    a delete reclaims nothing but a squash and gc does; transaction
    memory is about 2× the data, not 3–4×; the codelab's tag lookup and
    "check out a tag".
