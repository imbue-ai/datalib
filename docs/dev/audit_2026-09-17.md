## Headline

The repo is four months old (first commit 2026-05), 1,711 commits, 201 merged
PRs of which 113 came from `claude/` branches, ~186k lines of Rust and ~22k
of Vue/TS. That velocity shows in both directions: the parts that were
deliberately hardened in September (pinned render reads, the runner lock,
the API token, Bazel-pinned runtime trees) are good, and the parts that
were not reached are exactly where the problems are.

Four things need fixing before this is safe to hand to someone whose whole
private life it mirrors:

1. **Stored XSS in the app origin, escalating to code execution.** A message
   body from any source is rendered as raw HTML in the page that holds the
   API session, and the API can write a config whose step `command` is
   arbitrary.
2. **The applet ports are unauthenticated.** The whole grid index and every
   rendered document is served on a loopback port with no token and no
   `Host` check, reachable by any local process and by DNS rebinding.
3. **Every CLI and Docker user fetches qmd, latchkey and the embedding
   models unpinned at run time.** Only the macOS .app gets the
   Bazel-pinned trees.
4. **"One writer per doltlite file" is a convention, not a construction.**
   The runner lock guards the runner, not the file, and several shipped
   tools plus the search applet hold read-write handles on stores they do
   not own.

The rest of this document is the itemized version, by priority.

## P0 — fix now

### 1. Stored XSS → remote code execution (security)

- Renderers push message text into the markdown verbatim:
  `datalib/backend/etl/chat-common/src/render.rs:439-444`. Only reaction
  lines are escaped. Plain-text email bodies are raw; HTML email goes
  through `htmd` which strips only `script`/`style`/`head`
  (`providers/email_render/src/render/render.rs:694-700`).
- The UI renders that markdown with `new MarkdownIt({ html: true })` and
  injects it with `v-html` (`datalib/ui/src/cards/ChatBody.ce.vue:90-92`,
  `:340`). There is no DOMPurify or any sanitizer anywhere in
  `datalib/ui/src`. Shadow DOM is not a security boundary.
- The session cookie is `HttpOnly; SameSite=Lax` and attached
  automatically, so script in the page can call `GET /api/config` (secrets
  verbatim), read every document, and `PUT /api/config` +
  `POST /api/sync/jobs` to run an arbitrary step `command`
  (`dag/src/config.rs:1065-1069` says a custom command is arbitrary code by
  design). In the Tauri shell `withGlobalTauri: true` also exposes the
  dialog/opener IPC.
- Scenario: one crafted Slack DM, WhatsApp message or email. Next sync,
  next open.
- Fix: DOMPurify with an allowlist matching what renderers emit
  (`div.msg[id][data-section-uuid]`, `details/summary`, `audio/video`,
  `span[data-edge-id]`, same-origin `iframe[src]`), plus a CSP
  (`script-src 'self'`) on the served `index.html` so a bypass has nothing
  to run. Escaping at render time would also be right but does not cover
  the stores already on disk.

### 2. Applets serve everything with no auth (security)

- `unified_index` binds `127.0.0.1:<ephemeral>` and serves `/search`,
  `/docs`, `/chat/{uuid}`, `/asset/...` with no auth and no `Host` check
  (`datalib/backend/applets/src/unified_index/mod.rs:73-95`). The slack
  applet is a hand-rolled HTTP server, also unauthenticated
  (`applets/src/slack/mod.rs:327-345`).
- The gateway's `require_token` protects `/applet/...` only when reached
  through `datalib-http`. `forward()` (`http/src/applets.rs:773-776`) adds
  no credential.
- Threats: any other local user or process (multi-user machine, sandboxed
  app that can open loopback); a web page via DNS rebinding (no cookie
  needed; the ephemeral range scans in minutes). `auth.rs:1-18` explains
  this exact attack for the gateway; the applets reintroduce it.
- Fix: pass a secret to each applet at spawn (`applets.rs:92-97` already
  sets env), require it as a header in both applets, add it in
  `forward()`; independently reject any `Host` that is not the bound
  loopback address.

### 3. Unpinned run-time fetches on users' machines (supply chain)

- `npx -y @tobilu/qmd@2.8.3` (`runtime/src/qmd.rs:47-50`,
  `node_runtime.rs:84-95`) and `npx -y latchkey@3.11.0`
  (`etl/src/latchkey.rs:191-196`): top-level version only, ~170 transitive
  packages float, install scripts run, native addons (`node-llama-cpp`,
  `better-sqlite3`, `tree-sitter-*`) load in-process. The release tarball
  (`release.yml:341-355`) and `scripts/install.sh` ship binaries only, so
  every non-.app user hits this path at first sync. latchkey is the
  process that holds the user's session cookies.
- qmd pulls its three GGUF models from HuggingFace `main` on **every sync**
  (`qmd_indexer/src/lib.rs:85,227-230`, applet `mod.rs:121-126`), comparing
  an etag only. The build pins revision + sha256
  (`third-party/qmd_models/BUILD.bazel`); the runtime does not. A
  re-upload silently swaps the model llama.cpp parses in-process.
- perseus render downloads `Ancient-Greek-BERT` at `main` from inside a
  render step (`perseus_render/src/render/align/embed.rs:13-23,39-49`); the
  comment cites an hf-hub 0.3 bug, but the crate is on 0.4.3.
- Docs tell users to run bare `npx -y latchkey` (no version) with pasted
  secrets at 22 sites (issue #140, unchanged).
- Fix: put the three Bazel-built runtime trees into `//datalib/backend:dist`
  and the tarball; resolve `../runtime` from the binaries; gate `npx`
  behind an explicit env and log loudly when it fires; ship or
  hash-verify the GGUFs and set `pull: false`; pin the perseus revision
  and check sha256.

### 4. The signing job runs unpinned third-party code with certs in env (supply chain)

- `release.yml:513` `imbue-ai/use-vault-secrets@main` (mutable branch,
  issue #141 still open), `:504` `pnpm/action-setup@v6`, `:491-497`
  `sh.rustup.rs | sh` fallback + `rustup toolchain install stable`, `:152`
  `brew install cmake`, and `build-signed-app.sh:173`
  `pnpm dlx @tauri-apps/cli@2` (floating, no lock, resolved at signing
  time). 0 of 12 third-party `uses:` are SHA-pinned.
- Fix: full-SHA pins everywhere (Dependabot `github-actions` to keep them
  fresh); a `datalib/tauri/package.json` + lock for `@tauri-apps/cli`;
  `rustup toolchain install 1.98.0`; move the secret export after all
  third-party setup steps.

## P1 — architecture: the concurrency model and the data-flow graph

This is the section you asked about. Short version: the two pipeline edges
that were hardened in September (render reads ingest, grid_index reads
render) are pinned and read-only **by construction**. Everything else is
by convention, and the conventions have holes.

### 5. One writer per file is enforced per *runner*, not per *file*

What exists: `datalib-dag` takes `flock(LOCK_EX|LOCK_NB)` on
`<root>/system/runner-lock` (`dag/src/lock.rs:84-128`), `datalib-http` on
`<root>/system/lock` (`http/src/lock.rs`), both released by the kernel on
crash. The server's worker is a serial loop, so one server never runs two
runners; a hand-run `datalib-dag` is refused with the holder named. The
scheduler keeps at most one instance of a step in flight
(`scheduler.rs:295-300`). That covers the common case well.

What does not participate, each opening a pipeline store read-write with
no lock and no `read_only`:

| who | where | notes |
|---|---|---|
| `datalib-step` run by hand, every `providers/*/src/bin/*_ingest.rs` | `RawDb::open` | no lock code anywhere in `datalib_step` |
| **`datalib-fsindex`**, shipped in `:dist` | `fsindex/src/bin/fsindex.rs:22-24,77,132-135,168` | takes `--db` as any path, commits, **runs `dolt_gc`** on the same file `datalib-step ingest` writes |
| `datalib-dirtree-diff`, shipped | `dirtree_diff/src/bin/dirtree_diff.rs:80-99` | RW open of the user's stores |
| **`datalib-applet unified_index`** | `unified_index/src/dolt_repo.rs:123-126` → `core/src/store.rs:9-25` | **RW handle on `grid_index/db.doltlite_db`, `create_if_missing(true)`, unpinned, process-lifetime, never closed**; creates the file on a never-synced root |
| `datalib-doltlite` without `-readonly`, `scripts/doltlite_to_sqlite.sh:11` | | `dolt_status` from a reader kills the writer's commit (#400) |
| `datalib-migrate-config` | `migrate_config/src/main.rs:100` | non-atomic `fs::write` of `config.toml` while `datalib-http` watches that exact path; no lock; leaves `config.toml.orig` in the root |
| `yolink_make_fixture`, `qmd_indexer_bin` | fixture tooling | write pipeline-owned trees; guarded by convention |

Two more writer opens skip the rescue/schema-commit discipline entirely:
`datalib_step/src/grid_index.rs:44-50` and `BlobCas::open`
(`etl/src/blob_cas.rs:77-96`) use raw sqlx with `create_if_missing`, so a
crashed prior run's dirty rows fold silently into the next commit. On
non-unix the lock succeeds unconditionally (`lock.rs:237-240`).

The lint that stands in for a type (`scripts/lint_repo.py` checks 5 and 6)
is regex over a file glob. It misses `open_pool(`, `open_mirror(`,
`IndexedMarkdownStore::open(`, raw `SqlitePoolOptions`, and the crates
`unified_index`, `etl/render`, `datalib_step`, `history`, `core`. AGENTS.md
says "its two checks"; there are eight.

**Recommended shape.** Make the distinction a type, not a lint: one
`open_writer(path)` that takes a per-file `flock` on `<store>.lock` for
the pool's lifetime and is the only function that can return a handle with
`commit()`, and one `open_reader(path)` that opens `read_only`,
`create_if_missing(false)`, and returns a handle whose only content reads
go through a `Pin` it took at open. Then delete lint checks 4/5/6. The
`RawStoreHandle` derive and `pin.rs` already do most of the reader half.

### 6. Readers are pinned on the two pipeline edges, not elsewhere

Pinned by construction: `Pin` refuses `HEAD` (`etl/src/pin.rs:49-64`),
`Reads<'_>` is a mandatory parameter on shared loaders, `pinned_<t>` views
are distinct names so a forgotten install fails loudly; render →
`open_reader` → `RawRange::pin` → `install_views`; grid_index →
`open_for_reading` → `pin_for_reading`. Lint check 4's baseline is empty
and passes. This part is solid.

Unpinned, reading the working set of a store another process may be
mid-write on:

- the search applet, every query (`dolt_repo.rs:138-158`), during a
  `grid_index` batch — a torn view if uncommitted rows are cross-process
  visible (not measured; the two-process test measures commits, not open
  transactions);
- the slack applet (`applets/src/slack/mod.rs:225-231`) on a render store;
- `datalib_step/src/introspect.rs:215` `COUNT(*)` on bare tables in the
  render step, on a third connection, invisible to the lint;
- `history/src/lib.rs` `table_sizes` (counts the working set and
  attributes it to HEAD);
- `IndexedMarkdownStore::open_for_reading` exposes unpinned methods on the
  reader handle.

Fix is the same type split as #5; the applet should take a pin per
request (a `dolt_at_` view of HEAD) and drop it, rather than hold one
handle forever.

### 7. The blob CAS is never committed by 24 of 26 providers

- The only `dolt_commit` against a CAS is the seal path
  (`etl/src/raw_store.rs:172-175`), which runs only when the session was
  opened with `open_with_blobs`. Two processors do that (`claude` api,
  `garmin`); the other 24 call `ctx.open_store(db.pool().clone(), …)`. The
  seal code says "blobs before entities, always", so the intent is clear
  and the wiring is missing. The regression test builds a `SealState` by
  hand and cannot see this.
- Consequences: `pin::head` on such a CAS returns `None` (it can never be
  pinned, which is why `cas_objects` is read bare); `head_commit_at_path`
  returns the init commit forever, so the ingest step's reported version
  never reflects blob changes; the CAS pool is dropped inside `fetch`, then
  `ingest.rs:128` opens a second pool on the same file while the first is
  drop-closing (the #327 shape).
- Also: `BlobCas::open` bypasses rescue and schema-commit; nothing closes
  the CAS pool on the error path.

**Is doltlite the right store for blobs at all?** (Your question; the
evidence says probably not, and the code already behaves as if not.)

What the CAS uses of doltlite: one table, `INSERT OR IGNORE` keyed by
blake3, `SELECT bytes WHERE blake3 = ?`. What it does not use: `dolt_diff`
(never scanned), pinned reads (bare by design), history (commits happen
for 2/26 providers), rescue commits (bypassed), branches. A
content-addressed store of immutable bytes is its own version history: a
hash either exists or it does not, and nothing is ever updated in place.
Every feature doltlite adds over a plain table is therefore unused here,
while every cost is paid: the single-writer/commit-conflict discipline,
the prolly-tree write amplification (#489 saw a 105 MB store grow to
5.4 GB on one UPDATE; blobs are the largest rows in any store), no
streaming or mmap reads of large values (a whole attachment is
materialized into a `Vec<u8>` per `get`), unbounded history that GC
cannot reclaim without `dolt_gc` (#284 case 3: no refcount sweep), and
`-readonly` opens that hash the chunk store's root pages on open. On top
of that the bytes are kept twice — `blobs.doltlite_db` and each page's
`blobs/` directory (`chat-common/src/render.rs:246`), and #29 has been
open since June asking to serve by reference instead.

Options, in the order I would consider them:

1. **Plain SQLite for `blobs`.** Doltlite can create one
   (`doltlite_engine=sqlite`), the schema is unchanged, `sqlx` code is
   unchanged, and SQLite's own locking makes concurrent readers and one
   writer ordinary. Loses nothing the CAS uses today. Cheapest change.
2. **Files on disk, `blobs/<aa>/<blake3>`**, with `cas_objects` reduced to
   metadata (or kept in `entities`). Gives mmap, `sendfile`, `Range`
   requests, dedup by hash for free, and lets the render tree and the
   HTTP asset route link or serve the same bytes instead of copying them.
   A `BlobStore` trait with two impls keeps the choice per source.
3. **Keep doltlite but actually use it**: commit on every seal for all
   providers (the fix in #7), pin reads, and accept the costs. Only worth
   it if a blob's *absence* over time is something you want `dolt_log` to
   answer, which nothing asks today.

Whichever way, the decision belongs in `datalib/backend/etl/README.md`
beside the pool rules, and the `BlobCas` API is already narrow enough that
swapping the backing store is a contained change.

### 8. The DAG is declared but the fan-in steps do not consistently read it

- Steps get their inputs as ids in `DATALIB_DAG_INPUTS`, not paths. The
  graph is validated (cycles detected, `graph.rs:171-241`; unknown inputs
  dropped with a diagnostic).
- `grid_index` ignores its declared `inputs` and **lists the data root's
  directories** (`etl/render/src/grid_index.rs:565-576`): a source removed
  from the config but left on disk, or any foreign directory with a render
  store, is indexed. `qmd_index` does the opposite and reads `env.inputs`
  (`datalib_step/src/qmd_index.rs:36,105`). Two fan-in steps, two
  answers to "what are my inputs".
- Ingest steps that reach outside `<group>/ingest/` (from a full sweep of
  all 26): **garmin writes `~/.garth/oauth2_token.json` mid-run**
  (`garmin/src/auth.rs:196`); **fsindex writes `.fsindex.yaml` into the
  tree it scans** when `stamp_me_with_uuid` is on
  (`fsindex/src/ingest/options.rs:124-136`); **`sqlite_mirror` ATTACHes the
  user's SQLite file read-write** with no `mode=ro`
  (`sqlite_mirror/src/mirror.rs:221-230`), safe only because
  `snapshot: true` is the default; a **host-wide fingerprint cache** under
  `~/Library/Caches/datalib` shared by every root and 11 providers
  (`etl/src/fingerprint_cache.rs:142-160`); every HTTP body and the fully
  decrypted WhatsApp database transit `$TMPDIR`
  (`whatsapp/src/ingest.rs:147-153`); beeper shells out to the system
  `sqlite3`.
- Render steps outside the contract: **pdf re-reads the user's original
  file at an arbitrary absolute path** (`pdf_render/src/render/mod.rs:185`;
  the bytes never enter the raw store); **perseus reads a user-staged tree
  and hits the network** (#3 above); **slack and chatgpt fall back
  silently to a legacy JSON tree** when the store is absent
  (`slack_render/.../parse.rs:92-98`, `chatgpt_render/.../parse.rs:467-473`),
  bypassing pin, cursor and `consumed` — the exact "fallback that
  succeeds quietly" AGENTS.md warns about.
- Cursors are stored in the consumer's own store (good). An unusable
  cursor falls back to reading the store whole with a warning (good). The
  "sink contract" hazard (a consumer deleting on an empty read) is guarded
  in all 22 renderers; the one unguarded case is `put_document` unlinking
  a page whose row set is empty (`indexed_markdown.rs:288-290`). Three
  providers (airvisual, garmin, yolink) `bail!` on an absent store where
  the other 19 render empty and succeed.
- The sweep leaks bytes: `unlink_rendered` removes the `.md` and tries
  `remove_dir` on a parent that still holds `blobs/`
  (`indexed_markdown.rs:561-576`); `plots/*.html` are never tracked.
- `system/media/` is a dead `ServeDir` mount nothing writes
  (`http/src/lib.rs:141-146`); `ServeDir` follows symlinks.
- Versioning: `LAYOUT_VERSION` is wired into all 13 chat-common
  consumers, but **`contact-common` and `timeseries_render` have no
  version constant**, so a shared layout change re-renders nothing; notion
  has two `RENDER_VERSION`s (`render.rs:26` = 3 reported,
  `grid_rows.rs:17` = 1 stamped into rows); perseus's `alignment_pairs` is
  not in `render_params`.

### 9. The web app's concurrency model (issue #491 and around it)

Overall the shape is reasonable: axum handlers, `spawn_blocking` around
the blocking bits (applet proxy, config reload, usage walk), one serial
worker, broadcast channels fanned into one SSE stream, `notify` watcher
with a 300 ms debounce, a `RwLock` for registry state that is never held
across an await. The hazards are all of the same kind — check-then-act on
shared state with no single owner — and #491 names the biggest one
accurately:

- **#491 is still open in the tree.** `refresh_if_config_changed()` runs on
  the request path at `http/src/lib.rs:298` (`GET /api/frontend`) and
  `:367` (`/applet/` proxy). `PUT /api/config` (`lib.rs:826-856`) and
  `POST /api/config/init` do not reload the registry. The watcher publishes
  `ConfigChanged` (`watch.rs:188-192`) but nothing subscribes to it to
  reconcile. The #488 `reload` mutex is in place (`applets.rs:177,269`). The
  cost is what the issue says: a reconcile (up to 20 s per applet,
  `START_TIMEOUT`) can run inside a request.
- **`PUT /api/config` has no version check.** The wizard does
  read-modify-write client-side; two tabs, or a person editing the file
  while the wizard is open, lose each other's edits with no signal. Two
  concurrent PUTs also share one temp name (`config.tmp`), so the second
  rename fails with a 500 or renames the other's bytes. Fix: an ETag from
  the file's stamp, `If-Match` on PUT, a unique temp name.
- **Shutdown orphans the runner.** `worker.rs` holds a
  `std::process::Child` without `kill_on_drop`; on graceful shutdown or the
  Tauri shell's SIGKILL (`tauri/src/main.rs:169`) `datalib-dag` keeps
  running. The runner lock keeps a second runner out, and `datalib-dag`
  forwards SIGINT to its steps and reaps them, so stores are safe, but the
  next boot marks the job "recovered → failed" while the run may still
  finish. `datalib-dag` does not use `parent_watch` the way `datalib-http`
  and the applets do.
- **The proxy is a hand-written HTTP/1.1 client** (`applets.rs:759-832`):
  `Connection: close`, read to EOF, only `Content-Type` forwarded back,
  and the request line is built from the percent-decoded path so
  `%0D%0A` in a URL injects headers toward the applet (security #5, token
  holder only). `hyper`/`reqwest` are already in the tree.
- **#247 (two sources cannot sync at once)** follows from one runner
  process per root plus one serial worker. The right split is per-store
  locks (the type in #5) so independent sources can run in separate
  runner processes while fan-in steps still serialize.

## P2 — hygiene, dependencies, docs

### 10. Error handling

- **Issue #13 is still true at 51 sites**: `row.try_get(..).ok()` with a
  non-`Option` target cannot tell NULL from `""`/`0` and also swallows
  "no such column". Worst cluster is the API row mapper
  (`unified_index/src/dolt_repo.rs:194-200,412`). A further 123 sites use
  `try_get(..).unwrap_or_default()` with the same ambiguity. Fix:
  `try_get::<Option<T>, _>(col)?` and a lint check for `try_get(` not
  followed by `::<Option<` or `?`.
- **Failure classification is string matching** (`datalib_step/src/hints.rs:14-44`
  `.contains("HTTP 401")`, `"rate limit"`) over text that nine provider
  error enums each format differently; `datalib_etl::http::Retryability`
  exists and two providers use it (#350). Fix: `HttpError { status,
  retryability }` wrapped with `#[source]`, classify by downcast.
- **38 `warn!(…); continue` sites in ingest loops** drop records with no
  problem record (`claude/src/ingest/mod.rs:608` skips an org's projects,
  `export.rs:242,273`, `chatgpt …:348`, garmin ×5, google_takeout ×4);
  `download_problems` exists and gmail alone uses it.
- **Swallowed results that leave state wrong**: `worker.rs:183`
  `let _ = repo.finish_job(..)` leaves a job `running` forever if the write
  fails; `:282` `set_job_pid(..).ok()` makes a job uncancellable;
  `claude/src/ingest/db.rs:32` swallows a migration.
- **Reader pools never closed** in five render parsers (`chatgpt`, `claude`,
  `email`, `signal`, `slack` `…_render/src/render/parse.rs`) and `?` past
  `close()` in `etl/render/src/grid_index.rs:589-604`,
  `datalib_step/src/render.rs` (nine sites), and the slack applet
  (`slack/mod.rs:224-233`, a long-lived process). Nothing lints "close
  before the next open". Fix: a `with_reader(path, |pool| …)` helper that
  closes on every path.
- **Panics in long-running processes**: `scheduler.rs:190` `panic!` and
  `:574,801` `expect` inside the 616-line `run`; `runs/src/store.rs:499-672`
  `.expect("run store mutex")` on the writer thread (a poison silently
  loses every later log line); two mutex-poison policies in `http`; no
  `CatchPanicLayer`. `whatsapp_render …parse.rs:76` still creates a
  `Runtime::new()` per call, the hazard AGENTS.md documents.
- TS: 24 of 83 `catch` blocks are empty (seven in `api.ts`), 38
  fire-and-forget `void f()` with no `.catch`, no `unhandledrejection`
  handler.

### 11. Spooky action at a distance

- **The step protocol's env names are defined three times with no test
  tying them**: `dag/src/subprocess.rs:14-29`, `datalib_step/src/source.rs:11-15`
  ("mirrors … spelled out here"), `doltlite_raw.rs:736`; `LATCHKEY_GATEWAY`
  twice. A rename compiles and produces a step that cannot find its
  inputs. Fix: a dependency-free protocol const crate.
- **Hand-mirrored enums with no drift test**: `api.ts` `DagRunState`,
  `SyncJobState`, `ConnectState`, `ColumnType`, `live.ts` `LiveTable`. Only
  `ingestMethods.json` has a generator + golden. Extend that generator.
- 13 undocumented env vars (`DATALIB_DAG_CHECKPOINT_CADENCE`,
  `DATALIB_BINARY_DIR`, `DATALIB_STEP_BIN`, `DATALIB_CACHE_DIR`, `NPX_BIN`,
  `MINDS_VIA_DESKTOP_URL_PREFIX` read inside the shared HTTP client,

## What is done well

- `auth.rs`: 244-bit token, constant-time compare, `HttpOnly; SameSite=Lax`
  per-process cookie, launch token exchanged and stripped by redirect,
  0600 token file with a test asserting the mode, middleware outermost.
- Loopback by default everywhere; Tauri learns the port through a 0600
  url-file; no `0.0.0.0` bind anywhere in shipped code.
- Every `AssertSqlSafe` site binds values and interpolates only static
  identifiers; no `sh -c` anywhere outside tests; path handling gates
  (`is_sha256_hex`, canonicalize + `starts_with`) on the file-serving
  routes.
- The two pipeline read edges are pinned by construction, with a `Pin`
  type that refuses `HEAD`, a two-process test, and an empty ratchet
  baseline.
- Runner and server locks are `flock`, kernel-released on crash; the
  scheduler keeps one instance of a step in flight; SIGINT is forwarded to
  steps and children are reaped.
- Clippy `-Dwarnings` as an always-on aspect, `disallowed_macros`,
  per-crate unused-dependency errors, only 3 `#[allow(dead_code)]`, strum
  enums with serde-agreement tests, TS `strict` with 3 `any`.
- `lint_repo.py`'s structural checks encode real lessons (a download takes
  its store, a cursor sits beside its scope config) rather than style.
- The supply chain is in good shape for everything Bazel fetches; the
  gaps are what happens after install.
- Docs: `dag/README.md`, `etl/README.md`, `etl/macros/README.md`,
  `chat-common/README.md`, `entity_ids.md`, `step_protocol.md`, `applets.md`
  are tight and current; every plan carries an honest dated banner. The
  repo already contains the rules that would fix the docs; they have not
  been applied to the prose.
